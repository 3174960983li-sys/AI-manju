# 深度阅读与能力转化

## 一、先确定本轮在整条链路中的位置

系统精读保留原书论述的完整性，专题补读服务具体问题；两者都能产生知识，但不能混淆覆盖状态。知识文档面向理解与应用；SOP规定制作阶段、交接和返工；Skill将知识转成任务执行。这几层相互关联，不互相冒充。

只有设计请求就提交设计；明确要求制作Skill时才实现。用户已提供范围、偏好和授权时直接采用，不因阶段变化反复确认；新增费用、外发和重要破坏性动作不由本流程自动授权。

## 二、系统阅读的完整操作

1. **建立全书地图。** 核版本、材料性质、目录与作者核心问题，了解论述先后与关键依赖；选择本批完整章组，说明哪些前文需补读。只有目录扫描就标“结构已查”，不写成“已读”。
2. **连续阅读论述单元。** 逐段理解定义、主张、论证、例子与例外，检查相关图表、脚注及上下文。长度超过当前处理能力时按自然结构分批；搜索仅用于定位，不代替约定范围内的完整阅读。
3. **记录重要知识发现。** 保留概念、机制、步骤、判断、案例、反例、分歧及来源。论述性材料没有操作法时就解释其认识价值，不能编造原作者流程。
4. **辨认主题与联系。** 将分散在不同章节的相关内容联结；区分前置概念、因果机制、方法分支和应用边界。不要只按章节写互不关联的摘要。
5. **回读核对。** 从写出的结论回查来源支持；再从原文查遗漏的重要条件、例外与区别。机械检查只能证明定位和格式，不证明理解。
6. **保留续接信息。** 记录完成到哪里、仍未读什么、知识进入哪些文章、哪些发现暂存、下次从哪里开始。覆盖和必要图文确已完成后才能称全书已读。

扫描页、表格错位、旧格式和缺失媒体只影响相应范围，不必停止所有可独立完成的工作。重要结论受影响时说明并暂缓，不能靠猜测补齐。

## 三、一本书如何形成多篇知识文档

先按问题组织主题候选，再判断是否值得成文：是否具有独立使用场景、核心解释和必要依据？与现有文章是同义、补充还是不同任务？

- 同一问题已有正文：合入新知识或修订条件，不另造同义文章。
- 某问题可独立理解和使用：新建文章，并说明与相关知识的依赖。
- 只有一个例子或局部提醒：归入对应文章，不拆成碎片。
- 重要但本批来不及深入：留下来源、问题和下一步，不直接丢弃。

跨书比较时保留每份来源的定义、条件与立场，再说明对任务应怎样选择。来源数量不是独立性证明；同源摘录不算多个独立支持。允许未发现实质分歧，禁止为填表硬凑矛盾。

知识分类不局限现有SOP。当前用不到的历史、理论、审美或创作知识可以进入适当分类；不强迫它们立刻变成生产规则。

## 四、从知识到专业Skill的操作

### 1. 定义任务契约

明确用户会怎样提出任务、提供什么、需要什么成果、哪些选择应由用户决定、什么情况停止或返工。知识主题不能直接替代任务定义，例如“潜台词”是知识，“按人物目的修改一场对白并说明取舍”才是执行任务。

### 2. 核对现有SOP与Skill

读取当前适用版本，确认阶段、输入、交付、下游及返工关系。盘点已有能力：

| 条件 | 处理 |
|---|---|
| 已有Skill任务范围相同，只缺方法或判断 | 优先补强现有Skill |
| 只是题材、风格、参数不同 | 优先配置或参考模块 |
| 输入输出、职责、决策过程可独立复用 | 可以新建专项Skill |
| 知识仅提供理解或审美视角，尚无明确执行任务 | 保留知识，不强制产Skill |
| 新知识暴露SOP问题 | 提出差异、依据、影响和修订候选，不静默改标准 |

本项目已有`project-script-analysis`；不能因为读了人物书、场景书，就新建另一个同职责总分析Skill。

### 3. 建立知识与执行的对应关系

对重要执行节点明确：来源知识 → 适用条件 → 输入证据 → 判断与行动 → 分支或异常 → 输出及交接。只映射实际需要的知识，避免把全文复制进执行入口。

本地专用Skill可声明知识文档路径与版本；有独立分发要求时，将必要执行参考随包提供并保留来源、版本与许可。不能一面依赖本地绝对路径，一面宣称包完全可移植。知识正文仍只有一个维护原文；随包参考是有版本的执行摘要，不建立另一套独立知识库。

### 4. 制作与验证

确需实现时读取可用`skill-creator`，保持一个主制作流程，本参考提供任务与知识约束，不叠加第二套交付格式。若该Skill不可用，说明实际情况并按当前环境可用方式完成，不假称调用成功。

验证正常输入、关键缺失输入和容易误用的边界；实际检查产物是否符合用户目标、判断有无证据、分支可否执行、是否擅自补设定。已有Skill更新时检查仍有效的原行为有没有被破坏。

格式检查、来源支持、文字任务效果和媒体验证分别记录。没有实际材料就不能验证来源依赖任务；新编例子只验证相应方法边界。自查不称独立测试，不设置无依据的百分比或通过率。

### 5. 采纳、归档与维护

设计或制作结果保留明确状态。项目内候选包进入`研发候选`，用户审核通过后完整放`自研Skill`。用户明确要求更新已采纳Skill时，可以备份后更新原件，不因旧版本有“审核通过”标识而反复请求权限；新增部分按实际验证范围说明。

只同步已经存在且在授权范围内的安装副本；没有安装副本就不为“同步”额外安装。知识或来源发生实质变化时检查引用它的执行节点，局部修订，不自动升级所有正在制作的作品。

## 五、轻量续接记录

同一阅读任务维护一份必要记录即可，沿用已有任务记录，不每批复制一套管理文件。建议保留：

| 材料与版本 | 已读范围／图文缺口 | 知识主题与文章去向 | SOP／Skill关联与状态 | 下一起点 |
|---|---|---|---|---|

重要但未成文的知识在该记录中注明来源及待处理问题。正文出处留在文章末尾；提取缓存与详细中间稿留实际工作区。任务包完成按阅读覆盖、重要发现去向和产物可用性判断，不按文章或Skill数量判断。
