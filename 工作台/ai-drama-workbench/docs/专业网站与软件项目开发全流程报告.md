# 专业网站与软件项目开发全流程报告

版本：1.0  
日期：2026-10-31  
适用对象：个人开发者、小团队，以及“项目负责人＋AI开发助手”的协作模式。  
目的：提供从想法、立项、设计、开发、验证、发布到持续维护的完整执行路线。各阶段可以小步迭代，不要求先写完所有文档才开始编程。

> 本报告中的阶段划分、模板与执行建议是针对个人项目整理的方法，不是某一机构规定的唯一开发流程。安全与可访问性部分分别参考文末的NIST、OWASP和W3C原始资料。流程的详细程度应随项目风险、用户规模和团队规模调整。

## 一、先理解：你究竟在开发什么

网站与工作台并不互斥。网站描述访问和交付形态，工作台描述产品用途。通过浏览器使用的制作工作台，本身就可以是Web应用。软件则是更大的类别，还包括桌面程序、手机应用、命令行工具和后端服务。

| 形态 | 典型任务 | 主要工程关注 |
|---|---|---|
| 展示型网站 | 作品集、产品介绍、公共资料展示 | 内容、视觉、搜索可见性、加载、访问统计 |
| 浏览器业务应用 | 制作工作台、后台管理、协作系统 | 工作流程、数据、状态、权限、并发和恢复 |
| 桌面软件 | 本地剪辑、批量文件处理、离线创作 | 安装升级、文件权限、系统兼容、资源占用 |
| 移动应用 | 随时记录、拍摄、设备能力调用 | 小屏交互、离线同步、平台适配和发布渠道 |

选择形态前先回答：谁在什么设备上完成哪项任务？是否需要离线？是否多人同时使用？数据是否可以离开本机？有没有本地文件或硬件能力要求？不要先选最复杂的架构，再寻找使用理由。

专业程度体现在：目标明确、需求可验收、数据可信、故障可恢复、版本可追溯，以及有人能持续维护。页面数量或技术名词数量不是完成标准。

## 二、全流程地图与决策关口

主线：需求发现 → 产品定义与可行性 → 范围和计划 → 业务与交互设计 → 技术与数据设计 → 工程准备 → 分批开发 → 综合验证 → 试用 → 发布 → 运维 → 持续迭代。

这条主线不是只能走一次的瀑布流程。每个功能都可以经历“小需求—小设计—实现—验证—反馈”的循环；出现新证据时回到对应阶段修订，而不是无条件坚持最初假设。

| 阶段 | 必须回答的问题 | 最小交付物 | 进入下一步的依据 |
|---|---|---|---|
| 1 需求发现 | 谁有什么真实问题？ | 项目简报、用户场景、问题证据 | 找到需要解决的主要任务 |
| 2 可行性与立项 | 有价值、能完成、能维护吗？ | 可行性分析、关键风险与验证结果 | 决定继续、缩小、暂缓或停止 |
| 3 产品与范围 | 首版具体完成什么？ | PRD、首版边界、验收标准 | 范围清楚且资源匹配 |
| 4 业务与交互 | 用户怎样完成任务？ | 流程图、数据状态、页面原型 | 主流程与异常路径可走通 |
| 5 技术与数据 | 怎样可靠实现？ | 架构图、数据模型、接口约定、技术决策 | 高风险技术已有验证 |
| 6 工程准备 | 如何协作、测试和发布？ | 仓库、环境、规范、测试与检查流水线 | 换设备可按说明启动 |
| 7 增量开发 | 每一批交付什么可用结果？ | 可运行功能、测试、更新说明 | 功能完成定义满足 |
| 8 综合验证 | 整体是否满足要求？ | 测试记录、缺陷清单、风险清单 | 阻断问题处理完毕 |
| 9 用户试用 | 真实任务能顺利完成吗？ | 试用反馈、观察结果、改进决定 | 达到约定的产品目标 |
| 10 发布 | 出问题能发现、回退和恢复吗？ | 发布清单、部署与回退方案、版本标记 | 发布负责人批准具体版本 |
| 11 运维 | 谁负责服务和数据？ | 告警、备份恢复、故障处理记录 | 运行状况持续可见 |
| 12 迭代 | 下一次改进依据是什么？ | 需求池、复盘、路线图 | 基于证据安排下一版 |

## 三、第一阶段：把想法写成可验证的项目简报

### 你要做的事

先写一页，不写几十页愿景。说明目标用户、使用情境、当前替代方法、主要痛点和产品承诺。个人工具也需要需求证据：观察自己完成一次任务的操作、耗时、重复输入和出错位置即可。

按下面的句式描述目标：

“帮助【某类用户】在【具体情境】下完成【具体任务】，相较当前方法改善【可观察的结果】。”

以短剧工作台为例：帮助个人制作负责人在收到剧本后，保留原稿、核对场次并导出可追溯的制作数据，减少多份表格间重复复制和版本混淆。

### 手把手执行

1. 列出3—5个可能的用户任务。
2. 选出发生频繁、问题明显、你能够验证的一个主要任务。
3. 记录用户目前怎样完成，哪里中断或返工。
4. 写出可以观察的成功表现，例如“导入后能够找回原件，并定位每条场次数据的来源”。
5. 列出暂不确定的假设，例如“用户愿意接受先人工核对再保存”。
6. 用访谈、观察或小样验证最关键的假设，再决定是否投入。

### 交付与验收

交付《项目简报》：问题、用户、任务、价值、成功指标、边界、资源负责人。验收时应能让一个没有参与讨论的人复述：为谁解决什么问题，什么结果才算有效。

## 四、第二阶段：做项目分析，决定值不值得投入

分别检查产品、技术、资源和运营四类可行性。

| 类别 | 需要核对 | 验证方式 |
|---|---|---|
| 产品价值 | 是否已有足够好用的替代品；新工具改善哪项任务 | 对比真实任务，而非只列功能数量 |
| 技术能力 | 文件解析、数据规模、外部API、离线或实时要求 | 对高风险环节制作小型技术验证 |
| 时间与成本 | 开发、测试、接口费、运行、维护和返工投入 | 拆任务后给出估算区间及假设 |
| 内容与数据 | 数据来源、使用授权、隐私和保留要求 | 明确哪些可公开、哪些必须私有 |
| 持续运营 | 谁处理故障、更新依赖、支付运行费用 | 明确负责人和可承受的维护频率 |

技术验证只回答一个不确定性，例如“这种DOCX能否正确提取段落与表格顺序”，不顺手开发整个平台。

成本估算至少区分：一次性建设成本、每月固定成本、随使用增长的变量成本、风险预留。给每项写明计算依据；不要把未经验证的API单价或生成成功率当成确定值。AI应用还需要统计重试、失败和人工复核成本。

输出立项结论：继续、缩小范围、先验证某项、暂缓或停止。停止一个不适合当前资源的方案也是有效成果。

## 五、第三阶段：明确产品需求与首版范围

PRD即产品需求文档。重点是明确行为、限制和验收方式，不是堆积界面截图。

### 每项需求的最小结构

| 字段 | 示例 |
|---|---|
| 编号 | REQ-IMPORT-001 |
| 用户与目的 | 项目负责人希望导入剧本并保留原件 |
| 前置条件 | 已选择一个存在的项目 |
| 输入 | TXT/DOCX、大小和编码限制 |
| 操作与结果 | 上传、读取、核对、持久保存 |
| 异常 | 空文件、损坏文件、乱码、重复上传、磁盘失败 |
| 数据边界 | 当前项目隔离；不覆盖已有原稿 |
| 验收 | 重启后可读取；原件校验值一致；失败不产生半条记录 |
| 优先级 | 首版必须完成 |

### 功能需求和非功能需求都要写

功能需求说明能做什么；非功能需求说明在什么约束下做到，包括可接受响应、目标数据量、兼容设备、可访问性、备份恢复和安全要求。给可测条件和测量环境，不写“高性能、易用、安全”等无法验收的形容词。

例如：“在指定电脑、指定大小的测试文件下，导入过程有状态提示，失败时保留旧数据，并展示可以执行的处理建议。”数值目标应按实际场景设定，不直接照抄其他产品。

### 首版范围与变更

将需求分成首版必须、重要但可后移、可选和明确不做。首版要形成完整主任务闭环；不要求每个未来模块都先建页面。

新增需求要记录对时间、数据、测试和维护的影响，再决定替换现有工作、延后或增加资源。保留需求池，不因一句临时想法把正在交付的版本无限扩大。

## 六、第四阶段：先设计业务关系，再设计页面

业务模型决定哪些对象存在、怎样关联、谁能改变什么状态。它应先于界面细节。

以制作系统为例，先明确：项目、单集、剧本原件、场次、镜头、资产、批次、任务、检查和交付之间的关系。项目阶段不是内容对象；批次不是单集；检查通过也不自动等于采用。这些差异会决定数据库和界面是否可靠。

### 具体操作

1. 写出对象清单及定义，避免同一个词指代不同东西。
2. 给重要对象稳定ID，明确名称变化是否影响身份。
3. 写清一对多、多对多及可选关系。
4. 画状态流转，注明谁操作、需要什么条件、失败怎样处理。
5. 决定历史是否需要保留，旧版本怎样查询，更新是否使下游结果需要复核。
6. 区分“用户声明”“系统校验”和“实际验证”，避免界面显示超出证据的结论。

### 页面与交互设计

先画主任务的低保真原型，再确定视觉。每个页面至少考虑：正常、空数据、加载、成功、失败、无权限、冲突和部分完成状态。

让目标用户按任务操作原型，观察能否找到入口、理解状态、完成操作并恢复失误。不要只询问“喜欢这个页面吗”。

视觉设计再统一布局、字号、颜色、间距、表单、表格、提示和焦点表现。可访问性应在设计与实现阶段持续考虑，例如键盘操作、标签、对比、错误提示和状态反馈；WCAG 2.2提供可检查的Web可访问性准则。[W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/)

## 七、第五阶段：技术方案、数据库和接口设计

### 技术选择的方法

先列约束，再比较方案：现有技能、上线形态、并发量、数据类型、部署条件、团队人数、生态依赖和维护能力。记录选择理由、替代方案以及未来什么条件会触发调整。

对当前单人M1，继续用Python、Streamlit和SQLite完成业务验证是合理路线；是否更换前后端或数据库，应由后续的多人协作、交互和运行要求决定。数据库或框架名称本身不是产品专业程度的证明。

### 最小架构

```text
用户界面
   ↓
应用服务：用例、状态与业务规则
   ↓
数据访问／文件存储／外部服务适配器
```

业务规则不能只存在于表单按钮里。其他入口调用相同功能时，也应获得同样的校验。外部模型使用独立适配器，模拟实现与真实实现分别管理。

### 数据设计清单

- 主键、关联、唯一性、必填项和合法值。
- 版本、创建修改时间、操作者与关键操作记录。
- 删除、停用、归档的不同含义。
- 数据库迁移、备份、恢复、导入导出及容量增长。
- 并发更新策略，防止旧页面覆盖新修改。
- 文件内容与数据库元数据如何保持一致。
- 敏感字段、保留期限、访问权限和公开边界。

### 接口约定

即使尚未提供HTTP API，内部服务也应明确：输入结构、返回结果、校验错误、重复操作行为、超时和重试规则。涉及扣费或外部写入时，必须考虑重复提交和操作可追溯性。

把关键决策写成简短技术决策记录：背景、候选方案、决定、代价和重新评估条件。

## 八、第六阶段：搭建可重复的工程环境

可采用下面的最小结构，再按技术栈调整：

```text
project/
  README.md
  docs/                  需求、设计、决策、运行与验收
  src/                   业务逻辑与适配器
  ui/                    界面，或项目框架约定的入口
  tests/                 自动测试与测试数据
  migrations/            必要时单独管理数据库迁移
  scripts/               初始化、检查、构建等辅助脚本
  .gitignore
  依赖清单与锁定文件
```

目录应服务实际职责，单人项目可以更简单，不需要为了看起来规范拆出大量空目录。

### 手把手准备

1. 建立Git仓库并检查授权、公开范围和许可证；第三方代码或素材核对其使用条件。
2. 创建开发环境，明确运行时版本，锁定依赖。
3. 将凭据放在环境变量或适当的密钥管理设施中；配置示例只含占位符。
4. 将数据库、私人上传、缓存和日志排除出公开源码。
5. 写README，涵盖首次安装、启动、测试、停止、数据位置与常见故障。
6. 配置代码格式、必要的静态检查和自动测试。
7. 代码推送后让CI自动检查；外部付费服务测试默认模拟。
8. 换一个干净目录按README复现，避免依赖开发者电脑上未记录的状态。

简单项目可用主分支加短期功能分支。每次提交描述一个明确改动，保留可审阅差异，不强推覆盖他人工作。GitHub保存源码和版本；它不自动替代数据库备份或应用运行服务。

## 九、第七阶段：按完整用户任务分批开发

推荐每次交付一条能操作的纵向流程。例如“创建项目—上传—读取—保存—重启查询”，一次贯穿界面、业务、数据库和测试，而不是先写完全部数据库再写全部页面。

### 每项功能的执行循环

1. 选定一个需求编号，确认本次范围和验收标准。
2. 检查现有实现、数据和适用规则，提出最小改动方案。
3. 先验证最不确定的技术环节；需要时用模拟接口。
4. 实现业务规则与数据层，再连接界面。
5. 编写与风险相称的测试，覆盖关键成功、失败与数据完整性。
6. 实际运行主流程，核对用户能够理解反馈并完成任务。
7. 审查差异，检查敏感信息、无关变更和依赖影响。
8. 更新文档、完成记录和版本说明，再交给负责人验收。

### 功能完成定义

行为满足需求；异常路径合理；数据不意外丢失或串项目；必要测试通过；界面可操作；安装与使用说明已更新；已知限制公开；改动可回退或有恢复方案。

“写出了代码”“页面可以打开”“测试数量增加”都不能单独证明功能完成。

## 十、第八阶段：制定真实有效的测试与验收

| 类型 | 检查什么 | 例子 |
|---|---|---|
| 单元测试 | 独立规则与转换 | 编码解析、字段校验、金额范围 |
| 集成测试 | 模块间真实协作 | SQLite事务、文件保存、外部适配器 |
| 端到端测试 | 用户任务闭环 | 创建项目、上传、修改、导出、重启恢复 |
| 回归测试 | 修改后旧行为是否仍成立 | 更新场次模块后原件仍不可改写 |
| 数据迁移测试 | 老数据能否安全升级 | 升级前备份、关联保留、版本识别 |
| 性能与容量测试 | 约定数据量下的实际表现 | 大文件、多记录、目标并发下的延迟 |
| 安全测试 | 越权、输入、凭据、依赖等风险 | 跨账号读取、恶意文件、敏感日志 |
| 兼容与可访问性 | 目标设备能否使用 | 键盘、缩放、不同屏宽与浏览器 |
| 用户验收 | 是否满足实际业务目标 | 从真实剧本产出能用于下一步的数据 |

测试投入随风险调整。数据损坏、越权、扣费和迁移需要较强验证；简单可逆的排版修改通常不需要专门编写大量测试。

安全要求从需求和设计阶段开始安排。NIST SSDF强调将安全开发实践整合进软件生命周期；OWASP ASVS可用于把Web应用安全要求转为开发与验证依据。仅参考这些资料不代表取得认证或已经满足全部要求。[NIST SSDF](https://csrc.nist.gov/pubs/sp/800/218/final)；[OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/)

缺陷记录写明复现步骤、环境、期望、实际、证据、影响和修复验证。影响数据、权限或主任务的问题应优先处理；轻微视觉问题可在负责人明确接受后延后。

## 十一、第九阶段：真实用户试用与产品验收

技术测试通过后，让目标用户完成真实任务。首次观察时尽量不指导每一步，否则会掩盖产品不清晰的地方。

试用前明确测试版本、数据、任务、成功条件和禁止操作。试用后记录：任务完成情况、出错位置、求助次数、返工原因，以及用户需要但没有得到的信息。

反馈分清需求缺失、交互问题、程序缺陷、使用说明不足和暂不支持。把反馈转成可执行任务，不直接把用户的一句建议当作唯一实现方案。

验收报告对应需求编号，写明通过、未通过、部分通过及限制。接受遗留问题时，说明影响和后续安排。用户验收与测试人员检查是不同责任。

## 十二、第十阶段：发布前准备、上线与回退

公开源码、本机运行、局域网访问、受邀在线试用和公网生产，是不同的交付状态。必须明确本次发布的是哪一种。

### 发布前清单

1. 确定发布版本、代码提交、依赖和变更清单。
2. 在接近目标运行条件的环境验证配置和启动。
3. 确认数据库迁移、备份和实际恢复测试。
4. 配置需要的域名、HTTPS、访问控制和资源限制。
5. 核对开发配置、调试信息、示例账号和凭据是否泄露。
6. 核对监控、日志、错误告警、负责人和故障联系方式。
7. 检查主要用户任务、权限、上传、数据导出和失败提示。
8. 准备回退条件、操作步骤和数据兼容方案。
9. 如涉及个人信息或商业服务，按目标地区和业务核对适用义务；本报告不替代当地专业审查。

小项目也可以分步发布：先个人使用，再少量受邀试用，再决定是否开放。发布后立即做冒烟检查：服务可访问、关键数据可读写、核心任务成功、错误情况受控。

回退应用不一定能回退数据。若新版本改变数据结构，旧程序可能无法读取；需要事先准备兼容迁移、前向修复或从备份恢复的方案。恢复旧备份可能丢失备份之后的新增数据，应明确允许范围。

## 十三、第十一阶段：运行、备份、维护与迭代

上线后记录用户可感知的可用性、核心任务成功率、响应时间、错误率、数据与磁盘增长，以及实际运行费用。为需要处理的故障设置告警，不用无意义的大量通知代替监控。

备份制度至少回答：备份什么、多久一次、保存在哪里、谁可以读取、保留多久、怎样恢复。按业务确定可接受的数据丢失窗口和恢复时间；定期实测恢复，否则只能证明“存在备份文件”。

发生故障时：先控制影响并保护数据，记录时间和版本，再定位、修复、验证、恢复服务，最后复盘原因和改进。避免在事故处理中继续叠加不相关功能。

迭代依据包括用户任务反馈、缺陷、使用数据、维护负担和业务变化。每轮只选择有限目标，更新路线图和需求状态。无效功能可以明确停用，并提供数据迁移或导出路径。

## 十四、AI应用需要单独补充的开发环节

### 模拟验证与真实模型验证分开

模拟接口验证程序协议、保存、展示和失败处理；真实模型验证内容质量、稳定性、费用和延迟。模拟场次拆分成功不证明大语言模型能正确分析剧本。

### 真实接入前准备

- 明确允许发送哪些数据、授权范围和费用上限。
- 记录模型配置、提示词版本、输入版本和输出结构。
- 保留原稿；生成建议与采用结果分开保存。
- 对结构化输出做程序校验，不把模型返回直接当作可信数据库指令。
- 定义超时、重试、限流、取消与失败恢复，避免无限重试或重复付费。
- 上传文件和参考资料中的文本只当作数据，不能自动取得系统权限或触发工具。

### 建立评测集

准备能合法用于测试且覆盖典型难点的样本，包含正确预期或人工评价标准。场次分析可评估：遗漏和多拆、原文定位、人物地点准确性、字段完整性、人工修改量、延迟和费用。更换模型或提示词时，用相同评测集比较，再决定是否替换。

### Agent和SKILL的正确位置

先把稳定业务规则放进代码，再把可复用的专业方法放进SKILL；当确实需要工具调用、长任务和多步骤状态时，再增加Agent。SKILL描述方法，Agent负责执行编排，应用负责持久化、权限和可靠性。不要让提示词代替数据库约束，也不要让Agent自行批准开工、公开发布或高额支出。

## 十五、个人＋AI协作时的职责和交付方式

| 职责 | 项目负责人 | AI助手 |
|---|---|---|
| 目标与范围 | 决定目标、优先级、投入与边界 | 澄清问题、提出可选方案与影响 |
| 产品设计 | 确认关键使用流程 | 设计原型、写规则与验收条件 |
| 开发与测试 | 提供业务判断和必要访问 | 编码、测试、审查、更新记录 |
| 数据与费用 | 授权数据使用、付费和公开范围 | 按范围执行，提供实际证据 |
| 发布与验收 | 对具体版本做采用和发布决定 | 准备可审阅成果并核对执行结果 |

不需要为每种职责都新建一个Agent。小项目可以由同一个助手承担多个角色，但必须区分实施、自检与负责人验收；不能用角色名称制造独立审查已经完成的假象。

每次给AI的任务包可以这样写：

```text
目标：本次要让用户完成什么任务。
现状：源码位置、已有功能、问题与有效版本。
范围：本次必须完成什么，明确不做什么。
约束：技术栈、数据保留、费用、隐私和不可修改文件。
验收：操作步骤与可观察结果。
交付：改动文件、测试结果、运行方式、已知限制。
执行：先检查现有实现，做最小改动；不覆盖无关工作。
```

开发过程中优先报告：完成了什么、证据是什么、还有什么风险、需要负责人决定什么。不要只报告代码行数和工作量。

## 十六、建议维护的最小项目资料

| 文档或记录 | 解决什么问题 |
|---|---|
| 项目简报 | 为什么做、为谁做、目标是什么 |
| 需求与验收清单 | 本版做什么、如何确认完成 |
| 业务流程与数据模型 | 对象、关联、状态和历史怎样定义 |
| 交互原型 | 用户怎样实际完成任务 |
| 技术决策记录 | 为什么选择此实现、何时调整 |
| 开发任务与缺陷记录 | 谁处理、当前状态、影响范围 |
| 测试与验收记录 | 哪个版本在什么范围被验证 |
| README与运行手册 | 换设备怎样安装、运行和排错 |
| 发布、备份与恢复说明 | 怎样上线、停止、回退和恢复 |
| 变更日志与已知限制 | 版本变了什么、尚不能做什么 |

这些可以集中在少量文件中维护。一次决定只保留一个当前依据，历史另有追溯，不重复制造多份“最新版”。

## 十七、套用到当前AI短剧工作台

### 当前已经有什么

按本聊天已有交付记录，当前已有Python、Streamlit、SQLite的M1，以及12阶段导航、整剧—单集—场次—镜头、共享资产、批次、任务、人工确认、质检、资源、变更和交付的记录框架。候选版本报告64项测试通过；当前目录存在E盘运行版和可写工作区候选版，使用不同端口与数据。真实模型和媒体生成尚未接入。

这说明“原型代码及人工管理入口已经建立”，不能直接推出“需求研究、交互验证、安全审核、性能验证或正式产品验收都已完成”。测试通过只对应已执行测试的范围。当前确认记录主要依赖人工填写，仍需在真实项目中验证其范围、关联和操作负担。

### 下一步的专业推进顺序

1. **收敛产品目标。** 首先确定近期只服务你个人的哪条主要制作任务，把未来公开网站另列为后续版本目标。
2. **明确版本与数据。** 说明哪个目录是维护原件、哪个服务供试用、哪个数据库是正式数据；完成受控合并后再改变入口，不盲目覆盖E盘。
3. **补一份M1需求与验收基准。** 将已有界面逐项映射到需求，列出真正可用、仅为记录入口、尚未验证和计划移出的内容。
4. **完成一个真实项目闭环。** 导入授权剧本，建立单集与场次，人工修订，登记必要镜头和资产，检查并导出；观察操作是否有用，而非要求填满所有页面。
5. **修正业务和交互问题。** 优先处理数据混淆、重复填写、难以找到下一步、归属不清和失败恢复；需要时合并入口。
6. **补工程基线。** 干净设备运行、CI、数据迁移与恢复实测、依赖检查、发布记录和明确的源码同步策略。
7. **小范围接入真实模型。** 经你确认费用和数据范围后，用受限样本评估场次分析，再决定是否扩大；不同时接入所有平台。
8. **再做公开产品决策。** 明确目标用户与账号权限、数据隔离、运行预算和运维责任后，再选择是否改造架构、部署受邀试用并进入公开发布准备。

### 推荐里程碑

| 里程碑 | 实际完成标准 |
|---|---|
| M1个人可用 | 主要任务真实走通，数据安全保存和导出，用户能独立操作 |
| M1工程可复现 | 干净环境运行、自动检查、升级和恢复有实测证据 |
| M2模型辅助 | 小样本质量、人工修改量、失败处理和费用得到验证 |
| M3受邀协作 | 身份、权限、数据隔离、并发和运维达到试用要求 |
| M4公开产品 | 目标体验、安全、运行、支持和适用义务完成发布验收 |

里程碑根据证据推进，不给没有任务拆解和测量依据的固定工期。专业开发的下一步应从明确的需求和可验收任务出发，而不是继续横向增加页面。

## 十八、立即可用的启动清单

1. 写一页项目简报，选定一个主要用户任务。
2. 记录当前方法与主要问题，验证关键假设。
3. 明确首版范围、资源和停止条件。
4. 写出首条需求的正常、异常及数据验收条件。
5. 画主流程、对象关系和最小原型。
6. 对最不确定的技术做验证。
7. 建立可复现环境、仓库和检查方式。
8. 实现一条完整任务闭环，测试并真实操作。
9. 收集反馈，修正后再扩展下一条任务。
10. 按目标交付形态完成发布、备份恢复和维护准备。
