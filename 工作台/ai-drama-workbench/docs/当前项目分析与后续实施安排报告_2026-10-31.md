日期：2026-10-31  
性质：基于现有代码、数据库元信息、测试及远端版本的现状分析；包含建议采用的后续计划，不代表迁移、上线或付费调用已经获执行。  
审查方式：只读检查源码与文档、临时数据库自动测试、正式数据库只读元信息检查、运行服务健康检查、GitHub分支核对。未查看私人剧本正文，未变更正式数据库或运行版本。

## 一、结论与建议采用的方向

项目具备继续开发的基础，不需要推倒重做。目前应定位为：**面向个人制作负责人的、本地优先的AI短剧流程工作台原型**。

近期目标是让一个真实任务稳定完成：创建项目 → 组织单集 → 保留剧本原件 → 获取场次候选 → 人工核对与修订 → 保存历史 → 导出下一环节可用的数据。AI解析先维持模拟；后续真实接入单独确认数据与费用范围。

12阶段是业务导航与建设路线；整剧—单集—场次—镜头是内容结构；资产、任务、批次、检查与交付为跨阶段对象。三者保留，但不要求在首版逐一填满。

近期暂停新增大型模块、模型平台与复杂Agent，转入：**版本与数据整理 → M1需求基准 → 核心路径修复与简化 → 真实任务试用 → 工程与发布验收**。

公开网站保留为后续产品方向。当前先不做账号、支付、公开部署或技术栈重写。是否升级前端、数据库与架构，在目标用户、协作方式和实际负载明确后决定。

## 四、需要调整的重点

### P0：进入下一轮正式使用前解决

**1. 源码、运行入口和数据身份没有统一。**

E盘v4含现有数据，候选v6为空。应分别确定维护源码、正式数据、候选测试数据和备份的位置，记录其关系。先在副本上升级演练，再决定是否切换日常入口。禁止用空候选数据库覆盖正式数据库。

**2. M1范围与后续框架混合。**

M1最初聚焦导入、结构化场次、修改保存与导出；之后扩展为多个生产模块。应以真实主要任务重新建立验收基准，将生产台账保留为辅助工作区。功能保留不等于本版必须验收全部专业生产能力。

### P1：核心路径验收与正式候选发布前解决

**3. 确认范围仍主要由人工保证。**

production.py核对开工或交付确认的项目、关口类型和状态，但没有将确认范围与实际批次所含单集、具体版本及限定条件进行完整结构化比对。同项目的其他批次开工记录仍可能被错误引用。这是代码行为限制，不是本次发现有人已经误操作。

安排：建立确认对象、对象版本、条件及适用范围的明确关联；或者在这一能力完成前限制相关高级状态，明确由人工核对，不能宣传系统已自动授权。先写反例验收，再确定实现方式。

**4. 来源归属变化的下游影响尚未闭环。**

镜头引用场次，场次经剧本关联到单集；剧本归属可调整。已有记录保存部分资产、单集和确认版本，但未形成统一依赖变更与复核机制。应测试：修改剧本单集归属后，镜头显示的上下文、旧检查和批次记录是否仍可解释；必要时保存当时归属或提示复核。

**5. 数据升级与恢复证据不足以直接切换正式库。**

当前升级以创建缺失表、更新user_version及升级前备份为主，备份后缀使用原版本加一，不一定等于最终目标v6。后续应明确来源与目标版本、备份时间、重复升级行为及失败处理；先对v4副本做源原件校验、关联检查与恢复演练。

**6. 本地源码缺少正常的远程版本管理工作流。**

当前通过GitHub连接器发布有效，但本地工作区尚未成为该分支的正常检出。应在明确位置建立受控检出，保留远端现有提交，配置忽略规则与最小CI，并约定开发、候选与采用版本的区别。不在本次报告任务中擅自合并main或移动数据。

### P2：核心路径稳定后处理

**7. 导航与重复录入需要收敛。** 建议日常入口按“项目总览、剧本与场次、制作管理、规范与设置”分组。12阶段保留为业务导航，而非要求用户在多个页面重复填同一信息。分组只是设计候选，需原型验证后实施。

**8. 文档状态不一致。** 项目手册仍含旧Node主入口、早期公共规则状态与“下一轮”安排；旧03研究目录实际属于04；开发记录保留55测试/v5和64测试/v6多个增量。应新增清楚的当前状态索引，保留历史但标记替代关系，统一实际链接。旧研究草案不直接升级为正式规范。

**9. 未知值与实际数值应区分。** 资源表单默认为0，容易混淆“尚未估算/未登记”和“确实为0”。应定义未知状态、单位与精度，再设计统计；本轮不自动汇总成总成本结论。

**10. 引用位置不等于文件已验证。** 输出路径、清单和恢复说明目前主要是人工文本，不能自动证明文件存在、哈希正确、媒体规格合格或工程可恢复。界面应保持证据边界，后续按实际需要逐项实现检查。

## 五、整理方案：保留成果，收敛当前基准

- Python、Streamlit、SQLite及已拆分的核心业务逻辑。
- 已确认的12阶段、四层内容结构、四个早期关口及逐批/逐集决定权。
- 导入、原件保留、模拟场次、修订、导出和现有有效测试。
- 高级模块代码、专业框架及历史资料，暂不删除或批量重命名。
- 公开源码与私人项目数据分离；SKILL原件继续保留。

### 建议统一的身份

| 内容 | 建议定位 | 执行前条件 |
|---|---|---|
| 远端分支 | 当前代码发布依据，后续使用正常本地检出 | 核对提交及本地差异 |
| 候选v6源码 | 下一维护版的候选来源 | M1基准、差异与迁移验收通过 |
| E盘v4数据库 | 当前需要保护的正式数据来源 | 保留原件及可验证备份 |
| 候选数据库 | 测试/演示用途，不能冒充正式项目 | 测试数据与私人数据明确隔离 |
| 新日常入口 | 切换后仅保留一个明确推荐入口 | 副本升级、恢复与业务验收完成 |
| 停用版本 | 保留可追溯记录，停止推荐而非直接删除 | 记录替代版本及恢复方法 |

用户此前指定E盘为项目总目录，该偏好继续有效。本次报告及现有候选暂在可写工作区，不将它悄然确立为新的永久根目录。恢复E盘授权写入后，按受控方案落实最终位置；遇到审批阻碍不得绕过或静默更换。

## 六、M1建议范围与验收基准

### 本版必须交付

1. 创建、选择项目并保持项目隔离。
2. 建立单集规划，剧本可明确归属或保持整剧稿未分配。
3. 导入TXT/DOCX，保留原件、哈希、读取正文和限制说明。
4. 本地模拟场次候选，原文定位准确可核对。
5. 人工修改结构化字段并保留修订历史，不覆盖原文。
6. 导出明确版本的JSON/CSV，能够用于下一环节。
7. 重启后数据仍在；失败、重复操作与冲突有明确反馈。
8. 按说明在干净环境运行，并完成升级及备份恢复验证。

### 本版辅助功能

12阶段导航、人工任务与确认、镜头/资产/批次等记录入口可保留，但以试用状态标识，不要求用户填满。涉及放行或交付的高级状态在范围校验不充分时，不作为自动授权证据。

### 后移功能

真实模型、视频或图片生成、复杂Agent、多人协作、登录支付、公开部署、自动制作依赖校验和完整媒体质检。真实API前另行明确数据范围、预算上限和评测目标。

### 核心验收场景

| 编号 | 场景 | 通过依据 |
|---|---|---|
| A01 | 创建两个项目，分别导入 | 各自只见本项目资料 |
| A02 | TXT多编码和DOCX段落/表格 | 正文与原件对照；遗漏范围明确 |
| A03 | 同原件重复导入、同名不同稿 | 不重复、不误覆盖，稿件可区分 |
| A04 | 单集归属与多稿管理 | 当前归属清楚，历史有依据 |
| A05 | 场次候选与人工修订 | 片段来源完整，修改不改原文 |
| A06 | 导出指定修订 | 导出与界面选定版本一致 |
| A07 | 重启、坏文件、保存失败 | 旧数据不损坏，反馈可操作 |
| A08 | v4副本升级到v6并恢复 | 原件哈希/数量/关联核对，恢复可读 |
| A09 | 用户独立完成一次主任务 | 能找到下一步，明确输出用途，记录实际困难 |

不得把“64测试通过”替代上述人工与真实数据验收。真实样本的内容质量判断需要用户参与。

## 七、后续项目安排：六个工作包

安排采用依赖顺序和验收出口，不先承诺未经拆解的固定完工日期。执行第一个工作包后，再依据实际问题估算后续工时。

WP01与WP02中的只读盘点、文档和设计可并行准备；正式数据切换在迁移演练和必要确认后进行。WP04发现阻断问题时回到WP03，不跳过验证继续扩展。

### 每次开发的固定交付格式

- 本次需求编号、目标和不做范围。
- 改动文件及为何需要。
- 自动测试与实际操作结果，注明版本、样本和验证限制。
- 数据结构及兼容性影响，备份与恢复安排。
- 已知问题与下一工作包；涉及采用或正式数据切换时提交具体可审阅结果。

### 发布规则建议

开发完成 → 针对性检查与测试 → 差异审查 → 候选版本 → 用户业务验收 → 采用版本。公开源码可以保留未验收候选，但README必须标明状态。定时同步不代替验收，也不自动合并main。后续是否继续定时同步需另行安排；18:00任务已经执行一次，不默认转为每日任务。
