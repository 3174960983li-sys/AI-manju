# AI视频制作文件夹设计与现有资料管理方案

版本：V0.1征求意见稿｜日期：2026-10-23｜对象：E:\AI漫剧。

本稿依据02_持续迭代管理模型_V0.1_方案.md设计文件组织、现有资料处理和日常管理。当前只进行调查与方案编制，未按下列目标结构创建业务目录，未移动、重命名、删除、安装或改写现有生产资料。目录偏好等个性化选择正在征询用户；回答后形成V1.0待批稿，经用户批准才执行对应范围。

## 1 设计目标与依据

用户日常应能直接回答五件事：当前做哪个作品；用哪一版资料；下一步做什么；去哪里找方法；本次制作留下什么经验。文件架构围绕这些任务建立，不要求每次制作填写整套表格。

首轮盘点原有1155个文件，约12.77 GiB。公共知识、候选SOP、外来Skill、项目素材和成片均已有内容；本次补查发现，作品里包含历史绝对路径和Markdown本地链接，不适合不经引用检查就统一改名。约198处绝对路径文本匹配、194处本地Markdown链接匹配只是风险线索，范围包括管理文件；不是已经确认的失效链接数。

## 3 推荐的整体结构

下图描述逻辑分区。P02决定哪些分区采用实际目录、哪些只通过索引实现；不会同时复制两套相同内容。P03决定是否需要01_待整理。

```text
E:\AI漫剧\
├─ 项目中心.md                    已有，总入口
├─ AGENTS.md                      已有，项目协作入口
├─ 00_项目管理\                   已有，索引、管理模型、问题和盘点
├─ 01_待整理\                     候选，新增资料接收入口
├─ 02_知识资料\                   候选逻辑分区，承接理论和专业参考
├─ 03_SOP与制作标准\              候选，按范围管理流程和正式版本
├─ 04_Skill管理\                  候选，只存来源包、研发稿和安装映射
├─ 05_模板与提示词方法\           候选，可复用空白模板和表达方法
├─ 作品集\                        保留作品隔离
│  ├─ 开局鬼敲门\
│  ├─ 无限杀戮\
│  ├─ 植物大战僵尸\
│  └─ 神秘复苏\
└─ 灵感参考\                      可保留现名，独立于生产有效资产
```

每个作品和每套SOP的历史版本随其对象归档，避免所有历史文件集中进一个失去上下文的大仓库。已有只读SOP包可继续保留原位，通过03分区导航；若用户选择完整重整，再在映射表中确定物理目标。

| 分区 | 放什么 | 判定边界 |
| --- | --- | --- |
| 项目管理 | 全局项目目录、规则来源索引、问题队列、方案与批准记录、盘点快照 | 不复制每个作品的全部业务表格 |
| 待整理 | 用户暂未分类的新文件及最简来源说明 | 整理后有确定归属；不作为长期默认素材库 |
| 知识资料 | 理论书库、导演/分镜/美术/表演/声音/后期参考 | “读到的说法”保留来源和验证状态 |
| SOP与制作标准 | 按生产环节组织的流程，适用条件、输入输出及检查项 | 草案、试行和指定范围生效版本明确区分 |
| Skill管理 | 第三方原包、开发中的Skill、来源和安装版本映射 | 实际已安装Skill保持宿主发现路径，不随资料重排而移动 |
| 模板与提示词方法 | 空白模板、示例结构、可复用表达片段 | 具体作品实际投喂稿仍归对应作品；模板的唯一原件若已在SOP包则只建链接 |
| 作品集 | 剧本、设计、素材、投喂、生成结果、后期和交付 | 作品事实与资产不跨项目混用 |
| 灵感参考 | 未纳入项目基线的图像、声音、镜头和创意参考 | 被作品采用时登记具体用途，不能直接当审核通过的生产资产 |

## 5 作品内部的组织方式

建议以“逻辑阶段一致、实际目录兼容”为原则。现有作品通过一个入口说明文件把已有路径映射到阶段；新作品按需采用以下骨架，不提前铺设每镜空目录。

```text
作品名/
  项目入口.md             当前任务、采用版本、路径导航与缺口
  前期文档/               剧本、导演方案、分镜、资产清单及文字提示词
  美术/                   角色、场景、道具、特效、分镜参考及锁定资产
  视频生成/               实际投喂与生成任务、源视频、结果记录
  声音/                   配音、音乐、音效及采用信息
  后期/                   剪辑工程、字幕、时间线与工作导出
  交付/                   确认交付的文件及对应版本清单
```

这不是强制把所有作品改成新目录。已有“1：前期文档”“成片”“美术资产”等可继续使用；未知片段只标未知。进入长篇制作时再增加集、场、段或镜头层级，短片不强制套“集数”。Blender等工程位置及软件内媒体链接在依赖检查完成前保留。

**同一资料只设一个编辑原件。** 项目入口链接实际原件；生成任务记录引用实际提示词路径与版本。若必须独立保存当次投喂快照，用不可变快照和原件版本关联，不产生两份都叫“当前最终版”的编辑稿。

## 6 文件命名和版本管理

新文件可采用：`对象或段落_用途_V主版本.次版本_YYYY-MM-DD.扩展名`。例如：`第二段_视频提示词_V1.2_2026-10-23.md`。文件名不必重复完整项目名，已有命名不强行批量转换。

具体原则：

1. UUID、exec前缀等平台原图名保留，通过素材表补中文用途，减少断链。需要给人看的导出文件另用可读名称，并记原图来源。
2. 同一内容只有一个当前编辑入口；不同剧情分支分别保留，不能仅按日期覆盖。
3. 小版本表示不改变核心目标的修订；主版本表示流程、剧情或关键接口发生变化。版本增量应附简短变化说明。
4. “草稿/候选/采用/停用”和“未测试/已检查/真实输出”放在入口或索引字段中，不把所有状态堆进长文件名。
5. 文件存在、完成编辑、用户采用和生产验收分别记录。交付视频需指向对应版本和检查记录。
6. 路径保持适度层级；遇到长路径、软件读入限制时按实际工具调整，不盲目增加目录和命名字段。

## 7 最小管理记录

首期只维护四个入口，不引入数据库或统一大表。

| 入口 | 必要字段 | 更新触发 |
| --- | --- | --- |
| 项目总目录 | 作品、当前任务、状态、项目入口位置、主要缺口 | 开始/结束任务或换版本 |
| 资料与规则索引 | 来源、主题、阅读范围、适用条件、证据、现行入口 | 资料实际使用或方法提炼 |
| 每作品入口 | 当前采用稿、素材/输出位置、待决定项 | 剧情/分镜/素材/输出的有效版本变化 |
| 问题与复盘队列 | 问题、来源、最小下一步、结果、对应规则版本 | 遇到实际问题或结束一次迭代 |

生成任务只有在真实发生时才记录：任务ID、对应段/镜、提示词版本、实际输入、模型和设置、输出路径、采用片段及结果。需要成本分析时再补实际费用与工时；未知留空并说明。

## 8 新资料进入与经验回写

若P03选择待整理入口：用户可直接投放资料，能提供来源或用途时附一句说明。助手在用户发起整理或实际任务需要时处理：识别格式和来源 → 判断重复及所属对象 → 阅读必要内容 → 提炼可用规则或保留为参考 → 更新索引 → 按已批准方式归位。

若用户选择直接分类投放：跳过接收区，后续路径相同。任何模式都没有自动后台监听或无需触发的持续学习。

每次制作结束时保留五行复盘：遇到什么问题、依据什么判断、改了什么、实际结果怎样、更新哪条规则。只有可明确复用的方法才进入公共规则；角色设定、图号和剧情结果继续留在作品中。

## 9 重复文件、历史素材与备份

**首期清理方案：**只标重复候选与空文件，不删除。哈希相同才说明文件字节相同；是否保留还要考虑路径引用、原始资料包完整性和恢复需要。即使内容重复，也可先让目录索引只显示一个阅读入口。

**失败素材：**有诊断价值的失败图/视频关联到问题与提示词版本；普通未采用候选先保持原位。保留期限和清理阈值由P05决定，未获授权不自动删减。

**备份：**盘点CSV是清单，不是内容备份；同磁盘归档也不能应对磁盘故障。涉及迁移前，需要与用户确定可用备份位置、范围和恢复方式。当前只确认E盘有可用空间，不推断用户已有独立备份设备，也不自动启用云服务。

若未确定备份但希望先推进，可先执行已批准的原位索引整理；跨目录迁移保持待实施。

## 10 批准后的分阶段实施

以下全部为计划。本轮不开始其中的资料管理操作。

| 阶段 | 实际动作 | 交付及验收 | 回退 |
| --- | --- | --- | --- |
| A 原位建立入口 | 复核盘点，创建批准范围内的中文导航和对象分类表 | 找到当前资料、候选状态和缺口；所有新增入口链接可访问 | 移除本批新增导航，生产原件原位 |
| B 单对象试点 | 用户选定一个作品或公共资料类，先完成有效版本和来源映射 | 入口能解释关键文件用途；未知仍标未知，无假“当前最终稿” | 保留原稿，撤销本批索引/派生修改 |
| C 公共资料整理 | 按P02批准方式分类、建索引或迁移 | 每个实际处理文件有明确动作与原/目标路径；体积、数量、必要哈希吻合 | 根据操作清单逆向恢复，本批操作之外不动 |
| D 作品整理 | 按作品分批处理，先检查提示词、文档和工程引用 | 无重名覆盖、无缺文件；已知受影响引用已修复或列明阻断；必要时在原软件打开检查 | 同批还原文件与引用，保留旧版本和源快照 |
| E 日常运行验证 | 用一个实际任务走通检索、制作、检查、复盘 | 有真实记录支撑，字段维护量可接受 | 精简无用字段，规则恢复上一适用版本 |

批次大小按链接和工程依赖决定。发现未知覆盖冲突、关键文件无法读取、备份不可恢复或引用不能修复时，只停止受影响批次，其他原位设计与核对可继续。

**迁移前的可审阅清单格式：**对象｜当前路径｜目标路径｜动作（保留/索引/复制/移动/改名）｜原因｜引用影响｜校验方式｜回退依据。真正迁移前需填实际路径；本稿的分类表不冒充逐文件清单。

方案批准后，在已批准的目标和风险范围内连续完成各批次及验证，不逐文件反复请求确认。新增删除、外部发送、费用或与批准范围实质不同的迁移需另说明具体差异。

## 11 正式待批稿应包含什么

用户个性化反馈纳入后，提交V1.0待批稿，至少明确：选定主线与目录图、现有各类文件的处理动作、第一批对象、命名与版本规则、源文件与安装Skill边界、清理与备份政策、验收与回退方式。

批准以用户对具体版本和实施范围的明确答复为准。可以只批准“原位索引”或某个作品试点；其余部分保持待执行。对本方案提出意见、回答偏好问题或没有回复，都不视为开始整理的批准。

本轮已完成：读取现有模型与问题记录、补查目录用途和引用风险、形成此稿并发出个性化问题。未完成：用户偏好收敛、最终目标树确认、首批逐文件映射与实际实施。后续只继续方案设计，直至用户明确批准实施范围。
